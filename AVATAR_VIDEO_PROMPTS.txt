AVATAR VIDEO PROMPTS — for Google Veo 3.1, image-to-video
================================================================================

THE PROMPTS ARE ALSO DATA NOW — configs/avatar_clips.toml

  This file is prose: what each clip is for, why it is worded the way it is,
  and what went wrong with the last one. The prompts themselves, revised, live
  in `configs/avatar_clips.toml`, which is read by

      uv run python scripts/generate_avatar_clips.py --plan     # price it, send nothing
      uv run python scripts/generate_avatar_clips.py --all      # generate, measure, retry
      uv run python scripts/generate_avatar_clips.py --print-prompt turn-frame-right

  The tool generates a clip, runs it straight through the extractor, reads the
  measurement, and generates again **only** when the measurement failed. Every
  request is priced before it is sent and refused if it would cross `--budget`;
  every attempt is written to a ledger. Two clips have already been paid for
  twice because nothing measured them until days later.

  Paste by hand from `--print-prompt`, not from the blocks below, wherever the
  two disagree: the catalogue is what the tests check.

  WHAT CHANGED IN THE TURN PROMPTS, 2026-08-16 — the owner watched the stepped
  clip and it looked *rushed*: the head snapped between positions. So the moves
  between stops are now asked for as slow and gentle, taking about half a
  second, and the number of steps drops from eight to about seven so they fit
  in eight seconds without hurrying. The stops themselves are unchanged and
  still the point of the clip — a sweep, however slow, yields no still frame.

WHY VIDEO INSTEAD OF MORE STILLS

  One clip gives hundreds of frames of the same face under the same light, with
  the same framing. That is worth more than any number of separately generated
  stills, because the thing that ruins a still set is identity drift between
  them — and within one clip there is none.

  It also unlocks the change queued in PROJECT_STATUS: with dense coverage the
  engine can stop *blending* sources and start *selecting the nearest* one,
  which removes cross-fade ghosting by construction.


BEFORE GENERATING ANYTHING — three things to confirm on the plan being paid for

  1. IMAGE-TO-VIDEO from the attached portrait.png. Text-only generation makes a
     different person and every photograph, threshold and mask already tuned to
     this face becomes worthless.
  2. NO VISIBLE WATERMARK at this tier. Not "removable" — absent. A mark across
     the face makes a frame useless, and removing one is a licence breach in
     exactly the commercial case this is for.
  3. COMMERCIAL USE, output owned by you.

  These are from the checklist in docs/development/PROJECT_STATUS.md. The first
  is the one most likely to be missed and the most expensive to get wrong.


WHAT MATTERS IN THE OUTPUT

  - The face LARGE in frame. Frames are cut from this; the current portrait is
    1024x1024 and a small face in a wide shot is a downgrade.
  - SLOW, DELIBERATE movement. A frame taken during a fast movement is motion
    blurred and useless. Every prompt below asks for unhurried motion and brief
    holds — that is deliberate, not decoration.
  - LOCKED CAMERA. Any camera move changes the framing between frames.
  - CONSTANT LIGHT. The engine relights the avatar to the room; a source that
    changes brightness mid-clip poisons that.
  - ONE CONTINUOUS TAKE. No cuts.

  Attach portrait.png to every one of these.

GENERATED 2026-08-20 - eyes-slow-close, and why it is worded that way
================================================================================

  The take is on disk as `avatars/my_avatar/frames/eyes-slow-02`. The reasoning
  below is kept because the same trap catches every clip: a generator asked for
  a movement draws the reflex and holds the pose.

  Get the text with:

      uv run python scripts/generate_avatar_clips.py --print-prompt eyes-slow-close

  WHY IT EXISTED, AND WHY IT WAS FIRST. The owner's first report is that at
  20-30% of a closing the avatar decides the eyes are shut and puts the shut
  photograph on. That was measured on 2026-08-20, one photograph at a time,
  against the portrait's own resting eye opening of 0.0524:

      eyes_c012.png   filed at +0.122   opening 0.0203    39% of resting
      eyes_c022.png   filed at +0.221   opening 0.0190    36%
      eyes_c032.png   filed at +0.323   opening 0.0215    41%
      eyes_c042.png   filed at +0.423   opening 0.0205    39%
      eyes_c047.png   filed at +0.466   opening 0.0229    44%
      eyes_c056.png   filed at +0.558   opening 0.0221    42%
      clip_eyes_closed.png  - the photograph taken because the eyes were shut,
                              for comparison                        31%

  Six rungs, one picture. They span 0.019 to 0.023 with no order to them, and
  all six sit beside the photographs taken because the eyes were shut. So a lid
  reading of 0.20 is answered with a fully shut eye at full strength, which
  happens on 33.0% of the recorded driving clip. No threshold and no rate limit
  fixes that: the in-between pictures are not in the library.

  TWO TAKES ASKED FOR A CLOSING AND BOTH PRODUCED A BLINK. The old `eyes`
  clip, measured on video-07 at 50 ms per sample: one frame part-way down at
  2450 ms, then shut from 2500 ms to 6350 ms, then one frame part-way up at
  6400 ms. Two usable frames in eight seconds, and the face was 1120 px wide,
  so nothing was wrong with the framing. The first take of eyes-slow-close, at
  24 fps: open to shut in four frames, 3.1 seconds held shut, and a second
  blink the prompt had forbidden.

  A generator asked to close an eye draws a BLINK - a reflex, as fast as it can
  be drawn - and then holds the pose. Asking for it to be slower has failed
  twice now.

  SO THE PROMPT STOPS ASKING. The words "close", "shut" and "blink" are gone.
  It asks for a squint that deepens in three held steps, and the eyes never
  close: even at the narrowest the lids do not meet. A narrowed eye is a POSE,
  and a generator holds a pose - the same reason the turn clips ask for stops
  rather than a sweep - and a held pose is still, which is what makes a frame
  usable at all. Nothing in the clip is a shut eye, and nothing needs to be:
  both ends of the axis are already covered by photographs the library is happy
  with. What is missing is only the middle.

  AND A SECOND REASON THE OLD TAKES WERE MIS-FILED, fixed in code rather than
  in the prompt: `build_eye_ladder.py` fed every still to one tracker with the
  same timestamp, so MediaPipe - which runs in VIDEO mode and carries state
  between frames - thought the stills were one millisecond apart and lagged
  behind them. It reported a smooth ramp from 0.014 to 0.038 across frames that
  were in fact all wide open at 0.050. The ladder was built from the tracker's
  own lag rather than from the eyelids. Measured against a fresh tracker per
  still, passing the real millisecond - which the dumped filenames already
  carry - tracks the truth to within 0.003.

  FORMAT: 9:16, AND THE FACE AS LARGE AS THE FRAME ALLOWS. This is measured
  rather than preferred. The first take came back 1280x720 in 16:9 and its face
  was 320 px wide - under the 380 px floor, so the ladder builder refused every
  one of its 192 frames. video-07, which is 2160x3840 in 9:16, has a face
  1120 px wide. A vertical frame spends its pixels on a head, and a horizontal
  one spends them on the room either side of it.

  Resolution is the smaller question and 1080p is enough: at 9:16 that is
  1080x1920, and a face framed as video-07 frames it comes to about 560 px -
  already above the portrait's own 455 px, so anything beyond it is discarded
  by `_reduce_to` at load. 4K is not wrong, and the whole current library came
  from 4K clips, but backlog 16 measured 4K sources rendering *worse* than
  stills for reasons still not found, so there is no argument for paying for it
  here. Take whichever the site offers at 9:16.

  WHAT MAKES A TAKE USABLE. Not "it looks right", and not the ladder builder's
  own band table either until the timestamp fix above is in. The test is the
  frame-by-frame eyelid opening measured with the real timestamps: the take is
  good if the lids hold at three distinct openings between the resting eye and
  a shut one, for at least half a second each, and the face is at least 455 px
  wide. A take that jumps from open to shut in a few frames is the clip we
  already have, however slow it looked.

  ONE THING NOT TO WORRY ABOUT: the old rungs do not have to be deleted by
  hand. `build_eye_ladder.py --install` retires every `eyes_*.png` into
  `superseded-eyes/` and drops the matching manifest entries itself. That is
  the opposite of the turn ladder, where the deletion is manual and is the step
  that is easy and expensive to skip.

CLIP 4 — READY TO PASTE
================================================================================

  Copy everything between the lines, attach portrait.png, send.

  Two things in it are requirements rather than description, and both exist
  because of what the frames are for:

    - IT STOPS AT EVERY ANGLE, not just at the extremes. **The first version of
      this prompt asked for a slow continuous sweep with a pause at each end,
      and the ladder built from it is unusable**: measured on the near eye,
      which keeps its lashes and brow hairs at any angle, the turned rungs came
      out at **1.5-2% of the sharpness of the one frame where the head was
      still**. Every one of them is a smear. Worse, nothing caught it — the
      extractor's blur floor compares a frame with the third of a second around
      it, and in a continuous turn every frame in that window is blurred alike,
      so the softest sweep passes. (It now measures the near eye against the
      whole ladder and says so; see `extract_avatar_frames.py`.)

      So the movement has to be a series of *stops*: turn a little, hold still,
      turn a little, hold still. Each stop is one rung of the ladder and the
      engine wants one every three degrees, which a sweep with three pauses in
      it cannot give however slowly it is taken.
    - THE SHOULDERS DO NOT FOLLOW. The engine measures the *head's* yaw against
      the body. If the whole person rotates, the face is turned and the
      measurement says it is not.

  It sweeps the whole range rather than stopping at 40 degrees. The two far-turn
  photographs the library is missing are somewhere in that sweep, and so is every
  angle between them and centre — which no set of separate stills has ever given
  us. The extractor picks them by the same measurement the renderer uses, so they
  cannot come out swapped the way the hand-named pair did.

                                      turning only one way, which it did)
================================================================================

  The generator was asked for a stepped turn to the left and then to the right
  in one take, and returned a clip that only ever went one way. It is not worth
  arguing with: a ladder does not care how many files it came from, so ask for
  one direction per clip and merge them.

  **DIRECTION IS SAID TWICE, TWO DIFFERENT WAYS.** "Their left" and "the left of
  the frame" are opposite things, and which one a generator obeys is not
  knowable in advance — the first clip came back turning the owner's own right,
  which on screen is the face pointing at the *left* edge. So each prompt gives
  both readings of the same movement, and they agree. If the model follows
  either one it produces the same clip.

  **EIGHT SECONDS, AND THE MOVEMENT DOES NOT COME BACK.** The owner's generator
  caps at eight, and a return to centre would spend half of that re-photographing
  angles already covered. So each clip goes one way only and stops at the
  profile. About eight stops per side, which is a rung every five or six
  degrees — coarser than the three the ladder would like, and worth it, because
  every one of them is sharp and the thirty it replaces are smears.

  **The holds are the clip.** Only a motionless frame becomes a photograph, so
  the instruction is written as "stop" rather than "slow": a slow continuous
  sweep is exactly what failed the first time. The stated total — the head still
  for more than half the eight seconds — is there to be checked by watching it.

  Merging afterwards, once both are extracted:

    - The frames are named by the angle they were measured at — `turn_m12_0.png`
      for minus twelve degrees, `turn_p12_0.png` for plus — so the two sides
      cannot collide. Copy both sets into the avatar folder.
    - Concatenate the two `ladder_assets.json` arrays into the avatar's
      `metadata.json` assets list.
    - DELETE THE OLD RUNGS FIRST. Every `turn_*.png` from the first clip is a
      motion-blurred frame, and a blurred rung left in the manifest is chosen by
      angle exactly like a sharp one.

================================================================================

  ORDER, and it changed after the owner tested the application:

    1. CLIP 4 — HEAD TURNS, REGENERATED.  Not on this list before, because the
       clip existed. It is unusable: measured on the near eye, which keeps its
       lashes at any angle, its turned frames carry 1.5-2% of the detail of the
       one frame in it where the head was still. The whole ladder is a smear,
       and no geometry work can put back detail that was never photographed.
       Its block is under "CLIP 4 — READY TO PASTE" above, and it now asks for a
       STEPPED turn rather than a sweep.
    2. CLIP 3 — BROWS AND EYES.  The eyes are the standing complaint.
    3. CLIP 6 — MOUTH SHAPES.
    4. CLIP 5 — HEAD TILTS.  **Do not generate this one yet.** The tilt
       photographs were dropped from the engine on 2026-08-15 — they were
       active on 99.2% of frames at a median weight of 0.38 and their geometry
       is a tenth of a face away from the portrait's. What would make pitch
       usable is a ladder like clip 4's, and the ladder is one-dimensional: it
       brackets on yaw and nothing else. A second axis is a real change, not a
       parameter. Until it is built, this clip would sit unused.

  Every one of them holds each position for about two seconds. That is not
  padding. A frame taken mid-movement is motion blurred and useless, so the held
  moments are the only ones that become photographs. A clip that moves
  continuously for eight seconds yields almost nothing; a clip that stops eight
  times yields eight sources.

  AFTER GENERATING EACH ONE:

      uv run python scripts/extract_avatar_frames.py <clip> --out extracted/
      uv run python scripts/extract_avatar_frames.py turns.mp4 --out extracted/ --ladder

  The ladder run now prints each rung's near-eye detail as a percentage of the
  sharpest rung, and says so plainly when they are blurred. Check that line
  before building an avatar from the frames: if it warns, the clip moved too
  continuously and it is cheaper to generate it again than to ship it.

================================================================================
WHEN THE CLIPS ARRIVE
================================================================================

Do not sort frames by hand. The plan already recorded in PROJECT_STATUS is:

  1. extract frames from the video;
  2. run every one through scripts/check_avatar_photos.py, which measures
     identity, framing, lighting and pose, so a clip where the face drifted is
     caught rather than trusted;
  3. classify each usable frame by its own blendshapes and head pose — the same
     measurements the engine already uses to choose a source;
  4. switch the engine from blending sources to selecting the nearest.

  Step 4 is the reason the video is worth generating. It needs dense coverage,
  which is exactly what a clip gives and a set of stills never will.

  Keep the original video files. Frames can always be re-extracted; a clip that
  has been deleted has to be paid for again.
